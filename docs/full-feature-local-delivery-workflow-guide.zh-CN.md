# 全功能软件交付演练使用指南

## 1. 已安装内容

- 项目：`demo`
- 项目目录：`G:\Project\ai\demo`
- 工作流：`全功能软件交付演练`
- 工作流 ID：`workflow-full-feature-local-delivery`
- 当前版本 ID：`workflow-version-8aee1fc1-3a44-5f94-9908-830329043d60`
- 部署环境：`local-staging`
- 真实服务器：不需要

如果桌面程序在安装工作流前已经打开，请先刷新窗口或重启程序，使项目绑定信息重新加载。

## 2. 演练案例

本次案例是在空白 `demo` 项目中开发一个最小 Node.js 命令行工具 `release-check`。工具读取 JSON 文件并输出发布状态，同时提供测试和本地构建脚本。最终通过质量门禁和人工审批，将构建结果部署到本机 staging 目录。

## 3. 创建 Run

1. 打开左侧“项目”，确认当前项目为 `demo`，工作流显示为“全功能软件交付演练”。
2. 打开左侧“运行”。
3. 点击“新建 Run”。
4. Run 名称填写：`release-check 全功能演练`。
5. 任务目标填写：`在空白项目中创建 Node.js CLI release-check：读取 JSON 文件并输出发布状态，包含 node:test 测试、构建脚本和使用说明，最后完成本地 staging 部署。`
6. 执行工作区选择 `G:\Project\ai\demo`，模式选择“写入”。
7. 参数填写：

```json
{
  "packageName": "release-check",
  "runtime": "node",
  "deploymentTarget": "local-staging",
  "dryRun": true
}
```

8. 点击“创建 Run”。进入详情页后记下页面顶部的 Run ID，后文用 `<RUN_ID>` 表示。

## 4. 按节点执行

### 终端的两种使用模式

终端的“关联 Run”会读取当前项目的全部 Run，不受当前绑定的工作流版本限制。默认只显示仍可执行的 Run，并把当前 Run 排在最前面：

1. 使用“搜索 Run”输入 Run 名称或 Run ID，可以快速定位目标。
2. 勾选“显示已结束 Run”，可以查看状态为 `DONE` 或 `ARCHIVED` 的历史 Run。
3. 每个选项会同时显示 Run 名称、状态、工作流名称与版本、创建时间，选择前先核对这些信息。
4. 已结束 Run 仅支持加载历史终端会话和输出，不能创建新终端，也不能把独立终端绑定到该 Run。
5. 如果项目 Run 加载失败，可点击“重新加载 Run”；这不会影响“不关联 Run”的独立终端。

独立终端适合临时命令，不写入任何 Run：

1. 打开左侧“终端”，将“关联 Run”保持为“不关联 Run”。
2. 在“执行工作区”填写项目目录，选择终端类型后点击“创建终端”。
3. 执行命令并等待终端产生输出。
4. 点击“导出终端日志”。
5. 在按钮旁确认出现完整保存路径。日志位于项目目录的 `.workflow-platform\terminal-logs\...log`，内容会在写入前脱敏。

Run 绑定终端适合生成可审计的 Runtime Evidence：

1. 在“关联 Run”选择目标 Run，等待“绑定节点”加载完成，再选择目标节点。
2. 新建终端时，点击“创建终端”会直接完成绑定；如果终端已经在运行，则点击“绑定到 Run”，已有输出会回填到 Runtime。
3. 确认页面状态显示“已绑定到 Run”，且 Run 和节点选择器已经锁定。
4. 执行命令并等待终端产生输出。
5. 点击“导出终端证据”。
6. 在按钮旁确认出现完整 Evidence URI，再打开左侧“产物”，在对应 Run 下确认该 Evidence 已登记。证据文件位于该 Run 执行工作区的 `.workflow-platform\evidence`。

如果页面显示“终端暂无可导出的输出”，先执行一条能产生输出的命令再重试。保存成功以按钮旁出现的完整路径或 URI 为准。

### 节点 1：任务登记

1. 在 Run 页选择“任务登记”。
2. 点击“启动当前节点”。
3. 检查任务目标、参数和执行工作区是否正确。
4. 点击“完成当前节点”。

预期：节点变为已通过，“需求分析”变为可启动。

### 节点 2：需求分析

1. 点击“启动当前节点”。
2. Agent 执行区选择 `Codex CLI` 和“交互式终端”。
3. 提示词填写：`分析 release-check CLI 的用户故事、输入输出、异常场景和验收标准。按节点声明路径创建需求说明文件。`
4. 点击“启动 Agent”，在同页 Agent 标签中观察输出；需要补充时直接在执行器输入。
5. Agent 完成后确认文件存在：`docs/runs/<RUN_ID>/requirements/requirements.md`。
6. 点击“扫描并提交所需产物”。确认“已满足 1/1”。
7. 点击“完成当前节点”。
8. 打开“产物”页，确认需求说明已登记，然后返回 Run。

### 节点 3：技术设计

1. 启动“技术设计”。
2. 启动 Agent，提示词填写：`读取上游需求，设计 release-check 的目录结构、CLI 参数、JSON 校验、测试策略、构建输出和回滚方式，并按声明路径创建技术设计文件。`
3. 确认文件：`docs/runs/<RUN_ID>/architecture/architecture.md`。
4. 点击“扫描并提交所需产物”，确认成功后完成节点。

### 节点 4：方案审批

1. 启动“方案审批”。节点进入等待审批状态。
2. 点击 Run 资源中的“审批”。
3. 打开当前审批记录，阅读需求和技术设计。
4. 填写意见：`范围清晰，允许进入本地演练实施。`
5. 点击“批准”。
6. 返回 Run，确认“开发实现”已经可启动。

可以额外体验“暂缓”或“拒绝”，但会改变主流程状态；首次演练建议直接批准。

### 节点 5：开发实现

1. 启动“开发实现”。
2. 启动 Agent，提示词填写：`按照已批准的需求和技术设计实现 release-check。创建 package.json、src、test 和 README，运行测试，并按节点声明路径创建实现记录。不要扩大范围。`
3. 在 Agent 执行器中观察文件修改和测试输出。
4. 确认实现记录：`docs/runs/<RUN_ID>/implementation/implementation.md`。
5. 扫描并提交产物，然后完成节点。

### 节点 6：构建证据

1. 启动“构建证据”。
2. 打开左侧“终端”。终端模块可独立使用，但本次要关联当前 Run。
3. “关联 Run”选择本次 `release-check 全功能演练`，“绑定节点”选择“构建证据”。
4. 工作区填写 `G:\Project\ai\demo`，类型选择 `shell`，点击“创建终端”。
5. 确认状态显示“已绑定到 Run”，Run 和节点选择器已锁定。
6. 依次执行：

```powershell
npm.cmd test
npm.cmd run build
```

7. 如果出现高风险命令审批提示，核对命令后点击批准，体验终端治理流程。
8. 点击“导出终端证据”，确认按钮旁显示完整 Evidence URI。
9. 打开“产物”模块，在当前 Run 下确认终端 Evidence 已登记，然后返回终端。
10. 在项目中创建文件 `docs/runs/<RUN_ID>/build-evidence/build-evidence.md`，记录命令、退出码和构建输出目录。
11. 返回 Run，点击“扫描并提交所需产物”，成功后完成节点。
12. 再次打开“终端”，从历史会话中加载刚才的只读输出，确认终端记录可回放。

### 节点 7：自动测试

1. 启动“自动测试”。
2. 启动 Agent，提示词填写：`独立运行 release-check 的全部测试并检查关键异常场景。输出测试结论、失败信息和剩余风险。不要修改实现。`
3. 由于测试角色是只读/测试权限，请根据 Agent 输出创建 `docs/runs/<RUN_ID>/automated-test/test-report.md`。
4. 扫描并提交测试报告，然后完成节点。

### 节点 8：质量门禁

1. 启动“质量门禁”。
2. 点击 Run 资源中的“检查关卡”。
3. 选择 `quality-gate`。
4. 证据 URI 填写测试报告或终端证据，例如：`docs/runs/<RUN_ID>/automated-test/test-report.md`。
5. 确认构建成功、测试通过、必需产物齐全。
6. 点击“通过门禁”。
7. 返回 Run，确认“发布审批”可启动。

### 节点 9：发布审批

1. 启动“发布审批”。
2. 打开“审批”页。
3. 审批意见填写：`仅部署到本机 local-staging，不涉及远程服务器或生产凭据。`
4. 点击“批准”，然后返回 Run。

### 节点 10：本地 Staging 部署

1. 当前节点为 READY 时，点击“启动本地部署”。不要先点击普通“启动当前节点”。
2. Runtime 将执行受控的 `node -e` 命令，在工作区创建：`.workflow-platform/local-staging/deployed.txt`。
3. 等待节点自动完成。
4. 点击 Run 资源中的“部署”。
5. 选择部署记录，检查状态为 `COMPLETED`，并查看输出 `local staging deployment completed`。
6. 返回 Run。

这个步骤不会访问服务器，不需要 SSH、云账号或生产凭据。

### 节点 11：验收证据

1. 启动“验收证据”。
2. 在终端运行构建后的 CLI，使用一份示例 JSON 验证输出。
3. 创建 `docs/runs/<RUN_ID>/acceptance-evidence/acceptance.md`，记录输入、实际输出和验收结论。
4. 扫描并提交产物，然后完成节点。

### 节点 12：发布报告

1. 启动“发布报告”。
2. 打开“产物”页，汇总需求、设计、实现、构建、测试和验收记录。
3. 创建 `docs/runs/<RUN_ID>/release-report/release-report.md`，写明版本范围、门禁结果、审批人、本地部署结果、风险和回滚方式。
4. 扫描并提交产物，然后完成节点。

### 节点 13：复合收尾

1. 启动“复合收尾”。
2. 打开“审计”页，确认能看到工作流事件、Agent、终端、审批、门禁和部署记录。
3. 打开“恢复”页，查看诊断信息；点击“重建投影”，确认状态能够从持久化事件恢复。
4. 返回 Run，完成“复合收尾”。

预期：Run 状态变为 `DONE`，13 个节点全部通过。

## 5. 知识库闭环

1. 打开左侧“知识库”。
2. 展开“补录人工知识”。
3. 关联 Run 选择 `release-check 全功能演练`。
4. 标题填写：`本地 staging 发布检查清单`。
5. 内容填写本次演练总结，例如：`发布前必须确认需求、技术设计、构建、测试、质量门禁和人工发布审批；本地 staging 不需要服务器凭据。`
6. 点击“创建候选”。
7. 对候选执行人工“批准”。
8. 点击“发布”，确认生成知识文档并写入审计记录。
9. 可使用“回放发布记录”检查知识发布过程。

## 6. 成功检查清单

- Run 状态为 `DONE`。
- 13 个节点全部通过。
- Agent 执行器中存在需求、设计、开发和测试 Job。
- 产物页包含所有声明产物。
- 审批页至少有两条批准记录。
- 门禁页的 `quality-gate` 为通过。
- 部署页有一条 `COMPLETED` 的本地部署记录。
- 终端历史可以回放并导出证据。
- 审计页包含完整事件链。
- 恢复页可重建投影。
- 知识库中存在已发布的演练知识。

## 7. 重新安装

需要再次确认绑定时，在仓库根目录执行：

```powershell
python scripts/install_full_feature_workflow.py
```

脚本是幂等的：已存在当前格式的工作流时不会重复创建版本，只会确认目标项目绑定。
